Especificaciones Técnicas del Sistema (SDD) — Impulso Smart POSEste documento define las reglas de arquitectura, seguridad y lógica de negocio obligatorias para el proyecto Impulso Smart. Cualquier modificación, nueva funcionalidad o refactorización (manual o asistida por IA / Gemini CLI) debe cumplir estrictamente con estas especificaciones para evitar regresiones y parches improvisados (vibe coding).1. Contexto Tecnológico y OperativoFramework Backend: Django + Gunicorn + WhiteNoise.Base de Datos: PostgreSQL (Producción en Render) / SQLite (Desarrollo Local).Zona Horaria Operativa: America/Argentina/Buenos_Aires (UTC-3).Dominio de Negocio: Punto de Venta (POS) y gestión de inventario para comercio minorista de alta rotación (Pollería, Granja y Panadería), con soporte para pesaje fraccional (kg/gr), venta por monto directo y turnos de caja matutinos/vespertinos.2. SPEC-SEC-01: Endurecimiento de Entorno y SeguridadObjetivo: Garantizar que el despliegue en producción cumpla con el estándar OWASP Top 10 y las mejores prácticas de seguridad de Django sin entorpecer el entorno de desarrollo local.2.1 Variables de Entorno y settings.pyDetección de Entorno:DEBUG = os.getenv('DEBUG', 'False').lower() in ('true', '1', 't')IS_PRODUCTION = not DEBUG or os.getenv('RENDER', 'False').lower() == 'true'Validación de SECRET_KEY:En IS_PRODUCTION == True, queda prohibido usar claves fallback o que comiencen con django-insecure. Si SECRET_KEY no está definida en el entorno, el sistema debe lanzar django.core.exceptions.ImproperlyConfigured.Cabeceras HTTPS y Cookies (Activas únicamente cuando IS_PRODUCTION == True):SECURE_PROXY_SSL_HEADER = ('HTTP_X_FORWARDED_PROTO', 'https')SECURE_SSL_REDIRECT = TrueSESSION_COOKIE_SECURE = TrueSESSION_COOKIE_HTTPONLY = TrueCSRF_COOKIE_SECURE = TrueCSRF_COOKIE_HTTPONLY = TrueSECURE_HSTS_SECONDS = 31536000 (1 año)SECURE_HSTS_INCLUDE_SUBDOMAINS = TrueSECURE_HSTS_PRELOAD = TrueSECURE_CONTENT_TYPE_NOSNIFF = True2.2 Gestión de Superusuario y Credenciales en build.shProhibición de Hardcoding: Ningún script versionado en Git (build.sh, migraciones o comandos) debe contener contraseñas en texto plano fijas para producción.Inicialización Idempotente: La creación automática del superusuario en build.sh debe leer las variables de entorno DJANGO_SUPERUSER_USERNAME (default: 'admin'), DJANGO_SUPERUSER_EMAIL (default: 'admin@impulsosmart.com') y DJANGO_SUPERUSER_PASSWORD (default temporal solo si no se especifica: 'admin').2.3 Control de Acceso y Prevención de IDOR / XSS / SQLiORM Estricto: Prohibido el uso de .raw(), .extra() o cursores SQL directos sin parametrización.Protección de Vistas: Todas las vistas operativas deben estar decoradas con @login_required. Las vistas de anulación de ventas, ajustes manuales de caja y reportes financieros requieren validación de rol (@admin_required o pertenencia al grupo Encargados/Administradores).3. SPEC-INV-02: Resiliencia Operativa en Inventario y ProveedoresObjetivo: Asegurar que la velocidad de atención en el mostrador sea la prioridad absoluta. Ninguna restricción administrativa secundaria ni desfase de stock teórico debe frenar o bloquear una venta en vivo.3.1 Modelo de Productos y Proveedores (products/models.py)Relación No Bloqueante: El campo supplier (ForeignKey a Supplier) en el modelo Product debe ser opcional a nivel de base de datos y formulario (null=True, blank=True, on_delete=models.SET_NULL).Precisión Fraccional: Los campos stock, min_stock y las cantidades en SaleItem deben usar DecimalField(max_digits=10, decimal_places=3) para soportar pesajes exactos en gramos (ej. 0.350 kg).Semilla de Datos Inicial (Data Seeding): El script de despliegue debe asegurar mediante get_or_create la existencia de:Proveedores Base: Avícola Granja, Panificadora Central, Proveedor General.Categorías Base: Pollería, Panadería, Granja, Rebozados y Otros.3.2 Stock Dinámico con Auto-Ajuste en Ventas (sales/views.py)En rubros con desposte diario (donde del cajón de pollo surgen alitas, pata muslo, pechuga y menudos sobre la marcha), el sistema nunca debe rechazar una venta por stock <= 0.Algoritmo obligatorio al procesar cada ítem de una venta (dentro de transaction.atomic()):Obtener el producto con bloqueo de fila: product = Product.objects.select_for_update().get(pk=item_id).Sea $Q_{\text{venta}}$ la cantidad vendida y $S_{\text{actual}}$ el stock actual del producto:Caso A ($S_{\text{actual}} \ge Q_{\text{venta}}$):Se descuenta normalmente: $S_{\text{final}} = S_{\text{actual}} - Q_{\text{venta}}$.Se registra el movimiento de salida por venta.Caso B ($S_{\text{actual}} < Q_{\text{venta}}$ — Venta en descubierto / Desposte dinámico):Se calcula el excedente vendido no registrado previamente:
$$\Delta_{\text{ajuste}} = Q_{\text{venta}} - \max(S_{\text{actual}}, 0)$$Se genera automáticamente un registro en InventoryMovement (o modelo de movimientos equivalente) con:movement_type = 'AUTO_ADJUST_IN' (Ajuste Automático por Venta)quantity = \Delta_{\text{ajuste}}$reason = f"Auto-ajuste dinámico en POS por venta #{sale.id} (Stock previo: {S_actual})"El stock del producto se actualiza a $S_{\text{final}} = 0.000$.Beneficio de Auditoría: Al cerrar el turno matutino, el reporte mostrará exactamente cuántos kilos se vendieron en total y cuántos kilos correspondieron a "Auto-ajustes por desposte/stock no cargado", permitiendo cuadrar la mercadería física sin haber trabado la caja.4. SPEC-POS-03: Gestión de Turnos de Caja y Zona HorariaObjetivo: Evitar falsos bloqueos de "Debes abrir un turno de caja" ocasionados por diferencias entre la hora UTC del servidor en la nube y la hora local de Argentina.4.1 Configuración HorariaEn pos_system/settings.py:TIME_ZONE = 'America/Argentina/Buenos_Aires'USE_TZ = TrueToda consulta de fechas para reportes diarios debe utilizar django.utils.timezone.localdate() en lugar de datetime.date.today() o fechas UTC crudas.4.2 Validación de Caja Abierta (finance/ y sales/)Criterio de Turno Activo: Para determinar si se permiten ventas en el POS, el sistema debe consultar únicamente el estado del turno, sin filtrar por la fecha de apertura:active_session = CashSession.objects.filter(status__in=['OPEN', 'abierto', True]).order_by('-id').first()
Desbloqueo Rápido: Si un turno quedó abierto del día anterior, el sistema debe permitir operar en él o cerrarlo con un clic, pero jamás mostrar que la caja está cerrada si existe una sesión con estado abierto en la base de datos.5. SPEC-IMP-04: Importador CSV Tolerante a Fallos (Productos y Ventas)Objetivo: Erradicar los errores HTTP 500 al importar archivos CSV generados desde Excel, Google Sheets o anotaciones manuales.5.1 Reglas del Parser CSVDecodificación Multi-Formato: El lector de archivos debe intentar decodificar los bytes subidos probando secuencialmente: utf-8-sig $\rightarrow$ utf-8 $\rightarrow$ latin-1 (iso-8859-1).Autodetección de Separador: Soportar tanto coma (,) como punto y coma (;).Normalización de Cabeceras: Limpiar espacios en blanco, pasar a minúsculas y eliminar tildes de los nombres de columna (ej. Precio Venta, precio_venta y PRECIO deben mapear correctamente al campo sale_price).Sanitización Numérica: Antes de convertir a Decimal, eliminar símbolos $, espacios, separadores de miles y reemplazar comas decimales (,) por puntos (.). Si el campo está vacío o es inválido, asignar un valor seguro por defecto (0.00) o capturar la excepción.Aislamiento por Fila (Savepoints):Cada fila del CSV debe procesarse dentro de un bloque try...except con transaction.atomic() propio (savepoint).Si la fila $N$ falla, se registra el detalle en una lista de advertencias (messages.warning(request, f"Fila {N} omitida: {error}")) y el bucle continúa con la fila $N+1$. Nunca debe abortarse toda la petición con un Error 500.6. SPEC-SYNC-05: Arquitectura Híbrida Offline-First (PWA + Local Sync)Objetivo: Permitir que la pollería continúe facturando y registrando ventas en la computadora o celular cuando se corte el servicio de internet, sincronizando automáticamente con PostgreSQL en Render al recuperar la conexión.6.1 Capa Cliente (Frontend POS)Service Worker & Cache: Registrar un Service Worker (sw.js) que almacene en caché la interfaz del POS (/sales/pos/), hojas de estilo, scripts y el catálogo actualizado de productos en formato JSON.Almacenamiento Local (IndexedDB):Mantener una copia local del catálogo de productos (products_store) actualizada cada vez que se carga el POS con internet.Mantener una cola de ventas pendientes (offline_sales_queue).Detección de Conectividad:Si navigator.onLine == false o si la petición POST de venta falla por timeout/red, la venta se guarda en offline_sales_queue con un client_uuid único (UUIDv4) y created_at local.Se muestra en la barra superior un indicador visual: "Modo Sin Conexión — [N] ventas guardadas localmente".6.2 Capa Servidor (Endpoint de Sincronización en Django)Ruta: POST /api/sales/sync/Idempotencia por client_uuid:El modelo Sale debe incluir un campo client_uuid = models.UUIDField(null=True, blank=True, unique=True).Al recibir el lote JSON de ventas pendientes cuando regresa el internet, Django verifica si el client_uuid ya existe. Si existe, lo ignora y devuelve éxito (evitando ventas duplicadas si el internet micro-corta durante la sincronización).Si no existe, procesa la venta aplicando la regla SPEC-INV-02 (Stock Dinámico) y vinculándola al turno de caja abierto.7. Protocolo de Verificación Antes de Desplegar (Checklist para IA / Desarrollador)Antes de ejecutar git commit y git push origin master, todo cambio debe superar estas comprobaciones:python manage.py makemigrations --check --dry-run (Verificar que no falten migraciones de modelos).python manage.py check (Cero errores de sintaxis o configuración).Verificar que ninguna vista nueva carezca de @login_required.Verificar que todas las operaciones sobre saldos de caja y stock de productos estén envueltas en with transaction.atomic():.
